FACTS
- Runtime: livecode.html loads p5.js 1.11.11 + @strudel/web 1.0.3 from CDN (livecode.html:217-218). Canvas = createCanvas(windowWidth, windowHeight), colorMode(HSB,360,100,100,100), 2D renderer only, no pixelDensity() call so retina runs at 2x device pixels (livecode.html:329-333). Layers compiled via new Function(code), executed in insertion order inside draw(), each wrapped in push()/pop() with per-layer try/catch throttled to 1 error log/sec (livecode.html:335-357, 375-388). Layer z-order = insertion order; reordering requires remove+re-add (confirmed in autopilot/journal.md Round 5). /p5/fps route exists -> frameRate(fps) (livecode_server.py:500-502).
- Measured performance ceiling (autopilot/journal.md): fps 20 at ~250 polygon 'shards'; fps 15 with 6 layers + 81 buildings + 40 cars + meteors. Full-window canvas at default retina density is the visible bottleneck; per-scanline gradient loops (e.g. draw_desert_building.py SKY draws one line() per y-row every frame) are common and expensive.
- A nascent pre-generated asset library ALREADY EXISTS at autopilot/ — 58 JSON files in 6 categories: creatures/ (18: cat, dragon, robot, wizard, elvis, mermaid, unicorn, skeleton, ghost, alien, astronaut, dinosaur, fox, frog, gremlin, mushroomman, owl, snowman), worlds/ (8 full-screen backgrounds), floors/ (9), fx/ (6: balloons, bubbles, confetti, crowd, fireworks, spotlights), artscenes/ (5: flowfield, boids, lsystem, voronoi, attractor), musicscenes/ (12 Strudel genres). Format: {"name": <layer name>, "code": <minified JS>}, consumed by POSTing code to /p5/layer (a deleted 'rotator' script cycled them per rotator.log). Creatures are NOT parametric: position (cx=width*0.58), scale, palette all hardcoded in the code string.
- Two competing beat-sync conventions coexist: (a) scenes/compositions hardcode FRAMES_PER_BEAT=28.8 and compute beat = frameCount/28.8 (scenes/disco.py:11, disco_fx.py:34-36) — breaks when fps drops below 60 or tempo changes; (b) autopilot creature/floor assets use wall-clock: cps=window.state.cps||0.64; elapsed=millis()/1000 - state.t0; cyc=(elapsed*cps)%1 (creatures/cat.json) — fps-robust and tempo-aware via a state.cps convention.
- Visual techniques actually used (scenes/disco.py, compositions/scripts/*, full_show.py): beat-pulse envelope pow(sin(beat*TAU),4..8) everywhere; hue=(frameCount*k)%360 rainbow cycling everywhere; translate(width/2,...) centered radial symmetry (beams, rings, starburst, kaleidoscope, mandala); blendMode(ADD) low-alpha concentric-circle glow stacks; window.state particle arrays with life decay (sparkles/_dsp, energy/_ep, confetti); checkerboard/grid floors with phase-offset tile pulses; noise()-flickered triangle flames + sparks (draw_campfire.py); per-y scanline sky/ground gradients; deterministic integer hash2(i,j) for panel colors (draw_desert_building.py:133-137); drawingContext.clip() for a recursive scene-in-scene projection screen (projection_mural.py:119-124); coarse-grid brute-force voronoi with 2nd-nearest edge detection (projection_mural.py:206-263); depth-sorted circular arrangement with scale-by-depth for pseudo-3D (draw_campfire.py:259-275); strobe via frameCount%n; screen shake via translate(sin); 4-way mirrored particles; MULTIPLY dark wash.
- Structural sameness is INSTITUTIONALIZED in .claude/skills/p5.md 'Golden Rules' (lines 139-186): rule 1 = animate everything with frameCount sin/cos, rule 2 = 'Always work in HSB for vivid, cycling colors' with (frameCount*2)%360 hue, recipes are particle system / spiral / warped grid / kaleidoscope — the doc itself prescribes the samey look.
- Figurative drawing precedent is strong but bespoke: disco_dancers.py (583 lines) has 7 parametric humanoids with a pose-parameter interface {dy, tilt, hipX, lArm, rArm, lLeg, rLeg, spin, crouch, point, pointHand, circleArm} driven by beat-indexed choreography functions (getMove/getSoloMove, 16/32-beat phrases with snap/ease timing), per-dancer config {xFrac, sc, skin, shirt, pants, hair, belt, wave, solo} and mirror support; draw_campfire.py rider(x,y,sc,faceLeft,P) takes position/scale/facing/palette args. But every figure is hand-assembled from primitives — no shared skeleton, no reusable body-part functions, no pose library; the same afro/sunglasses/smile code is copy-pasted between disco_dancers.py and full_show.py (lines 1368-1495).
- Scene library visual coverage is thin: scenes/disco.py has 5 p5 layer functions (bg, floor, beams, ball, sparkles); scenes/jazz.py, hiphop.py, dnb.py have ZERO visual functions (music only). full_show.py's 19 sections reuse the same disco floor/beams/sparkles/dancers layers with parameter tweaks.
- createGraphics IS used and works: all 8 worlds/*.json cache a full-screen static background into a createGraphics buffer once (guarded by width mismatch check) then image() it each frame — the established pattern for expensive static content. blendMode(ADD/MULTIPLY/BLEND) heavily used. drawingContext (raw canvas 2D API) accessible and used for clipping. NOT used anywhere: filter(), loadPixels/updatePixels, loadImage/image-from-file, WEBGL, shaders, texture(), textFont; text() only as minor labels.
- State namespacing is ad hoc: window.state._dsp, ._ep, ._ff, ._bd, ._ls, ._vr, ._at, .confetti, .spaceBg/.arcticBg/etc, .t0, .cps — one underscore-prefixed key per system, no collision protection; improvise.py deliberately reuses ._ep across phases for particle continuity across layer-code swaps. Layer names also collide by convention (assets hardcode name 'floor', 'art', creature name).
- Autopilot instructions.md already names the wanted-but-missing territories: 'flow fields, L-systems, Voronoi/Delaunay, reaction-diffusion, differential growth, kaleidoscopes, mandalas, fractals, cellular automata, strange attractors', kinetic typography, isometric/voxel, camera moves — and bans 'lone breathing orbs, generic dot/particle fields with no subject'. An earlier ~90-scene queue of ready-made runnable scripts lived in /tmp/scene_queue/scene7-97.py (now empty — /tmp wiped), proving the pre-generated-scene workflow already ran once but was stored in a volatile location.
- REST latency ~10ms per curl call (AGENTS.md); every accepted /strudel|/p5 command auto-records into the show timeline; /p5/state route can set individual window.state keys server-side; syntax errors leave the old layer running (safe hot-swap).

OPPORTUNITIES
- Formalize and massively expand the existing autopilot/{creatures,worlds,floors,fx,artscenes} JSON library — the format, retrieval pattern (POST code to /p5/layer), and category taxonomy already exist and are proven on stage; the overhaul is 'more of this, but parametric, indexed, and in-repo' rather than a new invention.
- Make assets parametric instead of baked: creatures hardcode position/scale/palette inside minified code. Wrapping each asset as a JS function registered on window (e.g. state.lib.cat(x, y, scale, palette, pose)) or as a code template with a small JSON param block would let one asset serve as background extra, foreground soloist, or crowd member — the dancer pose-parameter interface (dy/tilt/hipX/arm/leg angles) in disco_dancers.py is a ready-made rig contract to standardize across all humanoids/critters.
- A figurative kit decomposes cleanly along lines already in the code: body rigs (dancer pose params), palette objects (skin/shirt/pants/hair per figure), props (sunglasses, helmet, EUC, roller skates, disco ball — all already isolated code blocks), stages/worlds (8 cached-buffer backgrounds), choreography (beat-indexed move functions). Extracting these into named, composable parts eliminates the copy-paste duplication between disco_dancers.py and full_show.py.
- Huge unclaimed generative-art territory for practice-session asset generation: reaction-diffusion, metaballs/marching squares, recursive subdivision, truchet tiles, circle packing, differential growth, cellular automata, dithering/halftone, ASCII, moiré/wave interference, kinetic typography (explicitly requested in instructions.md, barely attempted), isometric/voxel scenes, hand-drawn/wobbly line quality, feedback via createGraphics (currently only used for static caching — a persistent buffer drawn-into each frame gives trails/feedback/zoom-feedback for free), pixel-array effects, and WEBGL/shaders (would need a second canvas or hard recompile via /p5/setup — the hardRecompile path preserving state+layers already exists at livecode.html:409-432).
- Component taxonomy maps almost 1:1 onto the existing layer system: world/bg -> cached-buffer layer drawn first; floor; subject(s); fx overlay; post-effect = last layer (existing 'flash'/'energy' layers already do full-screen strobe/wash/shake this way — a translate/scale camera-rig layer or a feedback-buffer post layer slots in the same way). Needed conventions: (1) one reserved state namespace per asset instance (state.<layerName> = {}), (2) a shared clock contract (state.cps + millis-based beat, already used by autopilot assets) replacing hardcoded 28.8 frames/beat, (3) explicit layer-order slots (bg=0, floor=10, subject=50, fx=80, post=99) since z-order is insertion-order today, (4) palette passed as data, not baked into code.
- Performance headroom is cheap to claim: add pixelDensity(1) (likely 3-4x fill-rate win on retina), pre-render all static/scanline-gradient content into createGraphics buffers (worlds/*.json already demonstrate the pattern), and budget particle counts (~400-800 max seen). This directly attacks the fps 15-20 ceiling that also breaks frameCount-based beat sync.
- Fast retrieval during performance: assets as JSON with code strings mean zero-reasoning deployment (~10ms curl) — a grep-able index (tags: category, mood, palette, energy, subject) over hundreds of practice-built assets plus parallel subagents composing world+subject+fx+music from the library matches the planned architecture; the /tmp/scene_queue precedent shows pre-authored full scenes fired in <1s worked, it just needs durable in-repo storage.
- The p5.md skill doc should be rewritten as part of the overhaul — its Golden Rules actively train the agent into HSB-rainbow/frameCount-sine/centered-radial sameness; a technique-diverse cookbook (one recipe per absent territory, each with a distinct palette discipline) would shift live improvisation quality even before the asset library lands.

CONSTRAINTS
- Layer code runs inside new Function(code) in draw() every frame — no imports, no async, no top-level function declarations persisting across frames except via window/window.state; helper functions must be defined inside the layer code (they are, e.g. rider()/getMove(), recompiled every frame) or attached to window.state once.
- Canvas is 2D-mode only (createCanvas(windowWidth, windowHeight) in livecode.html setup); WEBGL/shaders require /p5/setup hard recompile which destroys and recreates the p5 instance (state+layers preserved but a visible hitch); mid-performance renderer switches are risky.
- Layer z-order = Map insertion order; no reorder API — an asset system must either always install layers in canonical slot order or add a reorder route; today reordering means remove+re-add all layers.
- window.state is a single shared global; assets must namespace their keys or collide (existing ad-hoc _prefix convention has no enforcement); particle arrays intentionally survive layer-code swaps (improvise.py relies on this), so a 'clear state on layer replace' policy would break existing behavior.
- Beat sync: frameCount-based timing (FRAMES_PER_BEAT=28.8) silently drifts when fps < 60 (measured 15-20 fps in heavy scenes) and breaks on tempo change; wall-clock millis()+state.cps is the reliable contract but requires every music-tempo change to also POST /p5/state {key:'cps'} — currently done only by autopilot assets, not scenes/compositions.
- Performance budget: full-window retina canvas, measured fps floor ~15 at 6 layers with a few hundred draw calls; per-pixel/per-scanline work each frame is unaffordable unless cached in createGraphics; pixel-array techniques (reaction-diffusion, dithering) need coarse grids or offscreen buffers at reduced resolution.
- Strict browser CSP does not apply here, but everything is CDN-loaded p5 1.11.11 — no p5 addons (p5.sound, p5.polar), no npm libs, no d3-delaunay; algorithms (voronoi, delaunay, physics) must be hand-rolled in plain JS inside layer code (existing voronoi is brute-force coarse-grid for this reason).
- Syntax errors keep the OLD layer running (good for live safety) but mean a bad asset deploy fails silently from the audience's perspective — asset QA must happen in practice sessions (server returns the compile error to the caller, and /errors exposes runtime errors, so automated validation is possible).
- Runtime errors are caught per-layer but throttled to 1 log/sec; an asset that errors every frame silently draws nothing — practice-time validation via /errors + snapshot diffing (autopilot_host.py already writes autopilot/snapshots/latest.png) is the verification path.
- Every accepted /p5 and /strudel command auto-records into the show timeline (shows/unsorted autosave) — bulk asset-library smoke tests against a live server will pollute captures unless /show/recording {enabled:false} is toggled.
- Assets stored in /tmp (previous scene_queue) were wiped; the library must live in-repo (autopilot/ dirs are the precedent; note shows/unsorted and media are gitignored — check .gitignore before choosing new asset paths).
- hush()/clear() and hard recompile preserve window.state — stale cached buffers (state.spaceBg etc.) survive scene changes and hold memory; a buffer-eviction convention is needed once hundreds of assets cache createGraphics buffers.
- Autopilot instructions.md contains durable user directives (≤60s livecode intervals, video interleave priority, no-silence transitions, no monotonous whiteouts, banned abstract orb/dot-field scenes) that any new performance loop must honor — the overhaul changes how scenes are made, not these stage rules.
