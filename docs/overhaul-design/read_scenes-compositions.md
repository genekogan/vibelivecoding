FACTS
- Scene primitive shape: every function in scenes/*.py returns {"name": str, "code": str} ready to splat into show.track(**...) or show.layer(**...) — code is a raw Strudel JS string (ending in .play()) or a p5 draw-body string. No class, no metadata, no route/type field; caller must know whether it's a track or a layer (scenes/__init__.py docstring, scenes/disco.py:16-262).
- Parametricity is nearly zero: of 50 scene functions, 48 take only `name` (a slot label). Only disco.drums(name, gain=0.82) and disco.bass(name, progression="c2 c3 c2 c3") take a musical parameter — and disco.bass's `progression` only substitutes bar 1 of 4; the Fm/Ab/Gm bars are hardcoded in the f-string (scenes/disco.py:36-49). Everything else (key, chords, gains, filters, hues, positions) is baked into the string literal.
- Counts: 50 scene primitives total — disco.py 11 (6 music + 5 visual: bg/floor/beams/ball/sparkles), jazz.py 25 (all music: 5 drums, 5 bass, 5 chords, 4 lead, 3 pad, sparkle, vox, breath_fx), hiphop.py 6 (all music), dnb.py 8 (all music). So 45 music vs only 5 visuals in the library. The real visual assets (~2,331 lines) live outside the library as module-level string constants (DANCERS, SKY, BUILDING, CAMPFIRE...) in compositions/scripts/{disco_dancers,disco_fx,draw_campfire,draw_desert_building,improvise,projection_mural}.py.
- Composition context manager (scenes/_common.py:68-191): three modes — live (posts each command immediately to http://localhost:{port}, waits for /status ready), --step (collects steps into a list, on __exit__ uploads via POST /show/load), --dump-steps (prints steps JSON to stdout, used by full_show.py run_script() to inline sub-script steps). Helpers: mark(label), track(name,code), stop, hush, cps, send_strudel, layer(name,code), remove, clear, pause (no-op in collect mode). --save PATH writes snapshot JSON. STEP_ROUTES whitelist (_common.py:45-50) gates what gets recorded as a step.
- .show.json step schema: each step = {"route": "/strudel/track|/strudel/stop|/strudel/hush|/strudel/cps|/strudel/send|/p5/layer|/p5/remove|/p5/clear|/p5/setup|/p5/state|/p5/fps|/p5/send", "payload": {...same body as REST route...}} plus optional "label" (section marker when route=="/show/mark" with empty payload) and optional per-step "dwell" (read by autoplay.py:125, spec grammar Ns|Nbeats|Nbars|Ncycles at autoplay.py:44). Top-level doc: {format:"livecode-show-v1", name, created, cps_at_start, steps} from server (livecode_server.py:527-536) but {format, name, created, default_dwell, steps} from Composition._snapshot (_common.py:121-129) — the two writers diverge on cps_at_start vs default_dwell.
- shows/full_show.show.json: 222 steps, 19 /show/mark section markers, 92 /strudel/track, 42 /p5/layer, 21 stop, 20 cps, 20 p5/remove, 2 /strudel/send (sample-pack loads), 136KB. Steps store literal final code strings — fully self-contained, replayable without scenes/.
- Copy-paste dominates: compositions/full_show.py (1,506 lines, 19 sections) does NOT import scenes at all — every section inlines raw code strings, byte-identical to scenes functions (verified: section 13 Disco == scenes/disco.py drums/bass/strings/wah/clav/shimmer verbatim; section 1 == jazz.drums_jazzy etc.). The scenes/ lib was evidently extracted from full_show.py but full_show was never refactored to use it. Only compositions/disco_set.py (53 lines) actually consumes the scenes library.
- Boilerplate duplicated 7x: the ~30-line post()/STEP_ROUTES/--dump-steps HTTP harness is independently copy-pasted into all 6 compositions/scripts/*.py files AND full_show.py AND _common.py. STEP_ROUTES itself is defined in at least 3 places (plus the server's own whitelist at livecode_server.py:110-118).
- Within scenes/, variation = copy-paste-with-mutation: jazz.py has 5 near-identical drums_* and 5 bass_* functions differing in a few literals; hiphop.pad is jazz.pad_minimal with gain .10 vs .13; hiphop.chords is jazz.chords_vibraphone with a different struct. No shared builders, no code composition beyond stack() inside a single string.
- Tempo/visual coupling: p5 beat sync uses FRAMES_PER_BEAT = 60/(cps*4) at 60fps; disco.py interpolates the constant 28.8 via f-string (disco.py:10-11), but compositions/scripts hardcode `frameCount / 28.8` literals (disco_dancers.py DANCERS constant) — visuals silently desync when cps changes (e.g. the crescendo section pushes 125→156 BPM).
- Implicit conventions that make composition work today: slot names collide on purpose (every genre uses drums/bass/chords/lead/pad so posting a new "drums" replaces the old); orbit allocation bass=3, chords=4, lead=5, pad=6, sparkle=7, vox=8 is consistent across all genre files but documented nowhere; p5 visual layers use ad-hoc window.state keys (_dsp, _ep) for particles.
- Sample-pack dependencies are implicit side effects: dirt-samples needed for bev:/breath: vox scenes (noted only in docstrings, jazz.py:432, hiphop.py:6), tidal-drum-machines JSON loaded once at full_show start via /strudel/send (full_show.py:164), github:yaxu/clean-breaks loaded mid-show inside improvise.py:51. Nothing machine-readable declares which asset needs which pack.
- Server timeline mechanics relevant to live use: every accepted STEP_ROUTES command auto-records into the timeline; navigating backward then issuing a new command truncates all future steps (livecode_server.py:506-516); /show/load resets state and replaces the timeline; autosave to shows/unsorted/ every 60s. Reproducibility doctrine (scenes/__init__.py): scenes are inlined at composition time so old .show.json files keep playing as scenes/ evolves.
- Discovery surface for an agent today: no index. To pick a scene the agent must read 13KB+ source files; the only searchable metadata is one-line docstrings. .claude/skills/livecode-compose.md is the hand-maintained catalog. test_steps.py is a Playwright regression (101 checks, 14 phases) over the step system.

OPPORTUNITIES
- The {name, code} → route contract is already the universal currency: server, Composition, autoplay, and .show.json all speak literal code strings posted to a handful of routes. A pre-generated asset library only needs to produce these strings — zero engine changes required to make retrieval-and-post fast (~10ms per curl). The bottleneck is purely generation/selection, which is exactly what pre-generation removes.
- Scenes are pure, side-effect-free string generators (scenes/__init__.py doctrine), so mass pre-generation during practice sessions is trivially safe: run generators offline, snapshot outputs (or param→output pairs) into an indexed store; the inline-at-compose reproducibility rule is preserved automatically.
- The show step schema already supports everything a compiled asset needs: per-step dwell, section labels via /show/mark, /show/load for bulk upload. A 'compile scene-graph → steps[]' pipeline can target the existing format-versioned livecode-show-v1 with no browser/server changes.
- jazz.py's 5-variant families (drums_jazzy/chill/complex/relaxed/busy differing only in a few literals) are proof that the existing corpus factors cleanly into templates + parameter dicts: pattern string, bank, gain envelope, fx sends are the axes. Converting 50 hand-written functions into ~10 templates x parameter grids yields hundreds of assets nearly for free, and dnb.py's staged CPS constants (0.42→0.85) show energy/tempo is already conceived as a parameter axis.
- The implicit orbit map (bass=3, chords=4, lead=5, pad=6, 7, vox=8) and colliding slot names (drums/bass/chords/lead/pad) are a ready-made 'mixing bus / slot' architecture: formalize it as library metadata and any retrieved music asset drops into a slot without clobbering unrelated tracks — enabling parallel subagents to each own a slot.
- ~2,331 lines of high-quality figurative p5 assets (dancers with 16-beat choreography phrases, campfire + EUC riders, desert building, voronoi mural, disco fx) are trapped as string constants in compositions/scripts/ with 7x duplicated HTTP boilerplate. Extracting them into the library instantly triples the visual catalog and creates the character/scene/fx taxonomy the overhaul wants (the penguin-DJ-under-disco-ball request decomposes into exactly these parts: character template + prop + lighting fx + floor).
- disco_dancers.py's data-driven dancer array (per-dancer {xFrac, sc, skin, shirt, hair, belt, wave, solo} dicts feeding one shared renderer) is the strongest existing example of the parametric pattern to generalize: one renderer + JSON parameter records = hundreds of distinct characters without new code generation at show time.
- FRAMES_PER_BEAT is the single tempo-coupling constant; making every visual template take cps (or reading it from a window.state key the server already can set via /p5/state) makes the whole visual library tempo-portable — currently broken at any tempo other than the one it was authored at.
- An index (JSON manifest or SQLite: id, kind=track|layer, genre, energy 1-5, cps range, key/mode, slot, orbit, deps=[sample packs], state keys used, one-line description, param schema) would let performance-time subagents grep/query instead of reading 13KB source files — directly attacking the 2-5 min latency. The catalog in .claude/skills/livecode-compose.md shows Gene already maintains this by hand.
- The 92 track / 42 layer literal code strings inside shows/full_show.show.json (plus everything in shows/unsorted/ auto-captures) are themselves a harvestable corpus: past performances can be mined into the asset library retroactively, and future practice sessions auto-record via the existing autosave — the capture pipeline for building the library already runs by default.

CONSTRAINTS
- Reproducibility doctrine must survive: assets are inlined at compose/perform time into literal code strings; .show.json never references the library. Old shows must keep playing when the library evolves (scenes/__init__.py). Never make playback depend on library lookups.
- livecode-show-v1 is a versioned format consumed by three readers (server load_show_from_file which hard-rejects other formats at livecode_server.py:556, autoplay.py, browser arrow-key stepping). Extend it only with optional fields (per-step dwell/label already are) or bump the version everywhere.
- Two writers already disagree on the top-level schema (server writes cps_at_start, Composition writes default_dwell); autoplay reads default_dwell. Any overhaul touching show I/O should unify this rather than add a third variant.
- Strudel code contract: track code must end with .play() when sent via /strudel/track; /strudel/send evaluate-mode code must NOT include .play(); setcps() unavailable (use .cps() or /strudel/cps); gm_* soundfonts unavailable; drum sounds need .bank() with real machines; sample packs must be loaded via /strudel/send before first use — library assets must declare pack dependencies so a compiler can emit the samples() step first (full_show.py:164 pattern).
- p5 layer contract: code is the body of a per-frame draw call compiled via new Function — no setup(), no createCanvas(); push()/pop() auto-wrapped; HSB colorMode(360,100,100,100); persistence only via window.state (keys are a global namespace — hundreds of concurrent assets need a state-key naming convention to avoid collisions like the current _dsp/_ep).
- Beat-synced visuals hardcode FRAMES_PER_BEAT (28.8 for cps 0.52) and assume 60fps; tempo changes desync them. Parametric visual templates must compute frames-per-beat from cps, and any /p5/fps change breaks the 60fps assumption too.
- Slot-name collision semantics are load-bearing: posting track 'drums' replaces 'drums'. The library must keep canonical slot names (drums/bass/chords/lead/pad/vox/fx) and the implicit orbit map (3/4/5/6/7/8) or concurrent subagents will overwrite each other's tracks and fight over shared fx buses.
- Layer z-order = insertion order (bg must be posted before floor before ball); the step compiler must respect ordering metadata, and /p5/remove of superseded layers (full_show does 20 removes) is part of scene transitions.
- Server-side timeline gotchas for live use: every accepted command auto-records; stepping backward then issuing any new command truncates all forward steps (livecode_server.py:512-513); /show/load wipes current state. A performance layer doing rapid parallel posts is also writing the recorded show.
- STEP_ROUTES whitelist is duplicated in at least 4 places (_common.py:45, full_show.py:53, each scripts/*.py, livecode_server.py:110-118); adding a new route type means touching all of them until deduplicated.
- f-string templating of p5 code requires doubling every JS brace ({{ }}) — already error-prone at 50 assets, untenable at 5,000; a different templating mechanism (string.Template, code-builder functions, or param-dict + shared JS renderers) is effectively mandatory.
- test_steps.py (Playwright, 101 checks, 14 phases, needs running server) is the only regression net over the step system — keep it passing; there are zero tests over scenes/ content itself (only syntax-by-construction).
- Python senders carry ~200-300ms import overhead vs ~10ms curl (MEMORY.md); performance-time retrieval should end in curl-or-persistent-process posts, not fresh python invocations per command (full_show.py's run_script subprocess pattern is the slow path).
