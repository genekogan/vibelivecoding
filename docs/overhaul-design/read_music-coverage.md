OPPORTUNITIES
- Genre whitespace is enormous: of ~25 broadly-known electronic/experimental genres, only ~10 have any recipe and only 4 have executable scenes — a practice-time asset factory could 5-10x genre coverage (trance, electro, italo, gqom, footwork, gabber, trap, UKG, afrobeat, gamelan, drone, concrète, Reich-phasing all buildable from already-documented primitives)
- Unused synthesis engines = instant timbral variety with zero new dependencies: 1000+ AKWF wavetables (wt_*), FM (fmh ratios give gamelan/bell/electro-bass territory), additive .partials() (organs, inharmonic bells), ZZFX (glitch/8-bit), noise oscillators (percussion, wind, texture) — none touched by current recipes
- .duck sidechain is documented and unused — one-line addition gives authentic house/disco/trance pump that current recipes fake with gain patterns
- .striate/.slice/.scrub + shabda freesound fetch unlock musique concrète / vaporwave / footwork sample-mangling territory; .scrub is tape-music in one call
- Stems are already pure functions returning {name, code} dicts (scenes/*.py) — the exact right shape to scale into a parametric library; jazz.walking_bass(scale) and disco.bass(progression) prove parametrization works, it just was never systematized
- Show format 'livecode-show-v1' captures literal code strings with labeled sections and per-step dwell — pre-generated assets can be stored as show fragments and spliced (the 'Riff template' at livecode-compose.md:172-185 already demonstrates array-splicing shows), giving O(10ms) curl-replay retrieval during performance
- Key parametrization is the single highest-leverage fix for sameness: template stems with {root}/{mode} placeholders (or systematic .transpose()) would break the everything-in-A-minor monoculture at near-zero cost since scale()/chord() strings are the only key carriers
- Per-orbit global reverb/delay suggests defining a fixed ORBIT CONTRACT in the stem schema (role→orbit table) so any two library stems are combinable without effect-bus fights; the implicit convention (bass=3, chords=4, lead=5, pad=6) is already ~consistent and just needs codifying + enforcement
- p5 stems should read tempo from injected state (server already has /p5/state route and knows cps) instead of hardcoding frames-per-beat — makes every visual asset tempo-portable across the whole library
- A machine-readable sample-pack manifest per stem (pack URL + load-time) enables a one-shot preload preamble at show start (browser caches samples), eliminating live 2-3s sleeps and the backward-replay re-load problem
- Practice sessions can also mine docs/strudel-examples-raw.md (Amensister, Flatrave, Belldub, Caverave etc.) — proven-good community material never ported into the scene library
- 6 of 9 documented drum machine banks are unused (Linn, RhythmAce, ViscoSpaceDrum, Compurhythm1000, CasioRZ1, TR505) — free timbral spread for electro/italo/lo-fi/space genres
- Pattern-algebra arrangement tools (.mask/.chunk/.when/.every) enable pre-baked intro/build/drop/breakdown variants of each stem — energy-level as a stem parameter rather than live rewriting

CONSTRAINTS
- Key collision: stems don't carry key metadata and ~all are hardcoded A-rooted (disco is C minor) — combining disco bass with anything else today clashes; library schema MUST include root+mode and stems must be transposable
- Tempo collision: pattern density is written against an assumed cps (hiphop stems assume 0.36, dnb 0.85) but the code string doesn't declare it; cross-genre stem combos play at wrong perceived speed — schema needs intended-cps + valid cps range, or a cycles-per-bar normalization convention
- room/delay are global per orbit (docs/strudel-reference.md:186): two stems on the same orbit overwrite each other's reverb/delay; any combinable-stem design needs a role→orbit allocation contract (orbits 2-8 currently used ad hoc)
- Same-named tracks replace each other (server keys tracks by name; convention names at livecode-compose.md:198) — a stem library must namespace or standardize roles deliberately; also every track update re-evaluates the whole stack() so one malformed stem code breaks the combined re-eval (errors surface via GET /errors)
- Sample deps must load BEFORE dependent tracks, take 2-3s, and live OUTSIDE the show timeline (backward-step replays every prior step — livecode-compose.md:249); gm_* soundfonts and github:tidalcycles/strudel-samples are permanently unavailable
- Cannot chain the same effect twice — second call silently overrides (docs/strudel-reference.md:462); composable 'effect layer' assets can't stack lpf-on-lpf etc.
- Every /strudel/track code string must end with .play(), exactly one .play() per stem (server strips + restacks); .cps is server-managed — stems must NOT embed .cps()
- p5 visual stems currently bake frames-per-beat constants tied to one cps — pairing music+visual assets across tempos silently desyncs unless visuals are rewritten to derive beat from injected state
- Gain staging is tuned in-context per recipe (absolute .gain values, no master compressor in use) — freely combining loud stems risks clipping; library needs per-role gain budgets
- shabda/freesound/github sample sources need network at load time — anything relied on live must be preloaded during practice (browser cache) or self-hosted; treat shabda as untested until exercised
- Show files are immutable literal-code artifacts by design (reproducibility rule, livecode-compose.md:44) — the asset library must generate/splice code strings, not runtime imports
- The stale scene catalog (livecode-compose.md lists 4 scene files that don't exist) shows index-vs-body drift is already happening — the overhaul's retrieval index must be generated from the assets, not hand-maintained
