FACTS
- REST surface (livecode_server.py:109-257): GET /status /state /errors /show/steps /show/save; POST /strudel/{track,stop,hush,cps,send}, /p5/{layer,remove,clear,setup,send,state,fps}, /show/{next,prev,goto,mark,recording,load,load_file,save_file}. All handled by one http.server.HTTPServer.
- HTTP server is SINGLE-THREADED (http.server.HTTPServer, not ThreadingHTTPServer, livecode_server.py:266) — concurrent REST calls from parallel subagents serialize; a slow /show/next replay blocks every other call.
- Latency path: every mutating call does HTTP parse -> ws.send to browser -> await browser response future (livecode_server.py:374-395, default timeout=5s). p5 layer set only does new Function(code) compile in browser (livecode.html:377) so ~5-15ms is realistic; /strudel/track re-evaluates the ENTIRE stack via window.evaluate (transpile + schedule), typically tens of ms, and can hit the 5s timeout if the browser stalls. Server was not running during recon so no live measurement; '~10ms' is plausible for p5, optimistic for strudel.
- p5 layer mechanics (livecode.html:328-432): p5 1.11.11 CDN, GLOBAL mode (window.setup/draw), createCanvas(windowWidth, windowHeight) => default P2D renderer, colorMode(HSB,360,100,100,100). Layers: Map name->{fn: new Function(code), code}; draw() iterates layerOrder (insertion order) calling each fn wrapped in push()/pop() (livecode.html:335-357). Compile errors rejected (old layer keeps running); runtime errors caught per-frame, throttled 1/sec/layer, forwarded to server via ws log_error -> /errors deque.
- Layer z-order = insertion order only; no reorder API. Updating an existing layer keeps its position; remove+re-add moves it to top (livecode.html:375-397).
- window.state = {} is a plain global shared by all layers, survives layer updates and hard recompile (hardRecompile saves/restores it, livecode.html:409-432). /p5/state does eval('window.state.KEY = <json>') (livecode_server.py:486-489) — key is dotted-path interpolated, so nested keys work; init_state() sets only-if-undefined (livecode_server.py:491-498).
- WEBGL: main canvas is 2D-only as shipped, BUT /p5/setup triggers hardRecompile (livecode.html:409) which destroys the p5 instance and re-runs arbitrary setup code — createCanvas(w,h,WEBGL) there would give a WEBGL main canvas. Alternatively any layer or /p5/send eval can createGraphics(w,h,WEBGL) + createShader/loadShader into window.state and image() it onto the 2D canvas. hardRecompile does NOT restore fps or non-default colorMode unless setup code re-sets them.
- Strudel mechanics: server keeps _tracks dict; every set_track/stop_track/set_cps calls _replay_all which joins ALL tracks into stack(t1,t2,...).cps(n) and sends with evaluate=true (livecode_server.py:440-453); trailing .play() is stripped server-side (:455-458). Browser: evaluate=true -> await window.evaluate(code, true) (transpiles mini-notation, auto-plays, replaces whole pattern aligned to the running clock); evaluate=false -> plain eval() for hush()/samples()/etc (livecode.html:646-673). cps lives only in server _cps and is appended to the stack string.
- Sample loading: initStrudel() loads nothing; livecode.html:304-318 preloads 4 banks at page init (tidal-drum-machines, uzu-drumkit, piano, vcsl from strudel.b-cdn.net). Extra packs loaded live via /strudel/send plain-eval samples(...). window.fetch is monkey-patched (livecode.html:224-240) to cache any raw.githubusercontent.com / cdn.freesound.org / *.wav/*.mp3/*.ogg/*.json URL in CacheStorage 'strudel-samples-v1' — practice sessions pre-warm the sample cache.
- AUDIO->VISUAL BRIDGE: NONE EXISTS. Zero FFT/analyser/amplitude/beat-phase code anywhere in livecode.html (grep confirms only getAudioContext for suspend/resume keep-alive at :634-643) and nothing in livecode_server.py pushes cps into window.state. But Strudel and p5 share the same page and the same AudioContext (getAudioContext() is global), so the bridge is one page-level snippet away.
- Step recording (livecode_server.py:506-516): every accepted POST to /strudel/{track,stop,hush,cps} and /p5/{layer,remove,clear,setup,state,fps} auto-records {route,payload,label} into _steps when _recording=True. CRITICAL EXCEPTIONS: /strudel/send and /p5/send return early and are NEVER recorded (livecode_server.py:205-207,222-224) — sample loads and eval'd helpers vanish from autosaves and from browser-reconnect restore (_restore_all :343-370 only replays tracks+layers, not setup/state/fps/sends).
- _record_step truncates all future steps if you issue a new live command while positioned mid-timeline (livecode_server.py:512-513) — stepping back then improvising destroys the rest of the loaded show.
- /show/next (step_next :598-636): finds next labeled boundary, replays every step from current+1 through end-of-that-section sequentially (each strudel step = full stack re-evaluate round-trip), with recording disabled. /show/prev and /show/goto do _replay_to: full reset (hush + clear) then re-execute steps 0..target — O(n) and audibly hushes mid-replay. /show/mark labels the CURRENT step (a section boundary = any step with a label).
- NO APPEND ROUTE: /show/load replaces the whole timeline AND calls _reset_state() (hush + clear all layers, livecode_server.py:518-523, 706-717) — loading kills live audio/visuals. Subagents cannot currently buffer pre-built sections onto a live timeline; the only workaround (load merged steps + goto back) replays everything from zero. A /show/append route would be ~10 lines: extend controller._steps without executing or resetting.
- /state (livecode_server.py:154-162) returns {ready, cps, setup, tracks: {name: full code}, layers: {name: full code}} — complete code dump. /errors (:163-165) returns {errors: [{ts, system: 'strudel'|'p5'|'video', message}]} from a deque(maxlen=50) that is never cleared by reading.
- WS relay backdoor (livecode_server.py:319-322): any WebSocket client on :8765 sending {type:'execute',...} gets it relayed verbatim to all other clients (the browser). This bypasses REST, recording, and server state tracking entirely — a subagent could drive p5/strudel/video directly over WS. It's also the only way to reach the 'video' target: livecode.html has a full-screen mp4 playlist player (target 'video', modes play/append/stop, auto-advance on ended, reports video_update back) with NO REST route exposing it (livecode.html:744-827).
- The HTTP server serves the whole repo directory as static files (livecode_server.py:104,123) with no-cache headers — pre-generated assets (images, JSON param packs, videos, shader source) dropped anywhere in the repo are instantly loadImage/fetch-able by layers at http://localhost:8766/<path>.
- Browser handshake: page sends {type:'ready', version:1, diag}; server rejects mismatched VERSION with a stale-browser warning (livecode_server.py:299-316). On reconnect, _restore_all re-sends stacked tracks + all layers. Autosave daemon writes shows/unsorted/jam_<ts>.show.json every 60s when steps grew (:570-587).
- Kiosk mode (livecode.py:53-75) launches Chrome with a FRESH tempfile user-data-dir every run — CacheStorage sample cache is cold on every kiosk launch (samples re-download from CDN).
- p5 layer code compiles once at set-time and runs every frame; there is no per-frame recompile cost. Pattern.prototype.play is already monkey-patched for logging (livecode.html:280-290) — precedent for patching Strudel internals from page script.
- Video steps are absent from _execute_step's route table (livecode_server.py:744-774) — even hand-authored show files cannot contain video sections today.

OPPORTUNITIES
- Audio-reactive bridge is cheap and high-leverage: add ~30 lines to livecode.html that (a) attach an AnalyserNode to the shared getAudioContext() output chain (superdough/@strudel/web has built-in analyser support — Pattern.analyze(id) + getAnalyserById — worth verifying in the 1.0.3 bundle) and (b) each rAF write window.state.audio = {fft[], rms, bass, mid, treble}; plus (c) one server-side line pushing cps + a beat-phase clock into window.state on /strudel/cps. Every existing and future layer could then read window.state.audio with zero API changes.
- /p5/state is a ready-made zero-recompile parameter channel: pre-built parametric layers that read window.state.params.* can be retuned in ~10ms per curl with no code generation at all — ideal for the template library ('penguin DJ' = 1 cached layer set + N cheap state pokes). It already auto-records into the timeline.
- /p5/send and /strudel/send are arbitrary-eval escape hatches: inject helper libraries (easing, palettes, sprite atlas loaders, shader compile helpers) once into window.* during setup, making individual layer codes tiny and fast to generate/retrieve. Caveat: sends aren't recorded or restored (see constraints).
- Static file serving means the pre-generated asset library can just be a directory in the repo: PNG sprite sheets, JSON parameter packs, GLSL files, pre-rendered mp4 stingers — layers loadImage('/assets/...') at runtime; the fetch monkey-patch even caches *.json/*.mp3/*.wav automatically.
- A /show/append route (extend _steps + optional label without executing or resetting) is the single missing primitive for subagent buffering: parallel practice/prep agents could push pre-built labeled sections onto the live timeline while the performer steps through with arrow keys. ~10 lines in livecode_server.py.
- The WS relay (:8765, type 'execute') is an existing high-bandwidth side channel for subagents — no REST serialization, direct browser eval, and the only path to the latent full-screen video player (pre-rendered scene interludes as mp4s).
- WEBGL/shader scenes are reachable today via /p5/setup (createCanvas WEBGL in hard recompile) or via createGraphics(w,h,WEBGL) buffers stored in window.state and composited onto the 2D canvas — the template library can include shader-based scenes without touching the harness.
- Sample-pack pre-warming during practice: any pack loaded once via /strudel/send samples(...) is cached in CacheStorage forever (per browser profile) — build a canonical 'warm the cache' script so performance-night sample loads are instant (but see kiosk temp-profile constraint).
- hardRecompile already preserves window.state and re-installs all layers — /p5/setup is a safe global-style switch (blend modes, pixelDensity, WEBGL, custom colorMode) between scenes.
- /state gives a full code dump — subagents can snapshot exact current tracks+layers before composing a transition, and /errors gives self-correction without screenshots.
- Reconnect restore (_restore_all) means a crashed/refreshed browser recovers tracks+layers automatically — pre-built shows are resilient mid-performance (except setup/state/fps/sends, which need re-sending).

CONSTRAINTS
- Single-threaded HTTPServer serializes ALL REST calls — heavy subagent parallelism against :8766 will queue, and each mutating call blocks on a browser round-trip (up to the 5s timeout). Either switch to ThreadingHTTPServer/aiohttp or route parallel traffic over the WS relay; note websockets sends are already async-gathered.
- Every /strudel/track change re-evaluates the ENTIRE stack of all tracks (stack(...).cps(n) through window.evaluate) — per-track cost grows with total track count, and one syntactically broken track silences everything until fixed (there is no per-track isolation like p5 layers have).
- /strudel/send and /p5/send are invisible to state: not recorded as steps, not in /state tracks/layers, not restored on browser reconnect. Any overhaul relying on send-injected helpers or sample loads must re-send them after reconnect and inject them into show files manually (routes ARE supported in _execute_step, so hand-authored show steps can carry them).
- /show/load resets state (hush + clear) and replaces the timeline; new live commands issued mid-timeline truncate all future steps (livecode_server.py:512). Buffering-while-performing requires the missing append primitive; do not naively 'load' during a set.
- step_prev//show/goto replay from step 0 with a hush+clear first — going backward is O(n) round trips and audibly gaps; long pre-built shows make backward navigation slower over time.
- p5 layer code is compiled with new Function — synchronous, no async/await at layer top level, no imports; persistent objects must live in window.state. Layer z-order is insertion order only (no reorder API) — template library must define a naming/ordering discipline or add a reorder route.
- Canvas is P2D global-mode p5 1.11.11 with HSB colorMode set in setup; templates assuming RGB or WEBGL must switch modes explicitly per-layer (push/pop isolates it) or go through /p5/setup hard recompile (which drops custom fps/colorMode unless the setup code re-sets them, and briefly destroys the canvas).
- gm_* soundfont instruments don't work in the @strudel/web CDN bundle; setcps() is unavailable (use .cps()/set_cps); .play() must not appear in evaluate-mode code (server strips trailing .play() but only at end-of-string, livecode_server.py:455-458).
- Kiosk mode uses a fresh temp Chrome profile per launch — CacheStorage sample cache and any prefetched assets are cold every show unless kiosk is changed to a persistent user-data-dir.
- Browser/version handshake: bumping VERSION in livecode.html requires matching EXPECTED_VERSION in livecode_server.py:299 and a hard browser refresh, or the server ignores the client.
- /p5/state builds JS via string interpolation of the key (window.state.<key> = ...) — keys must be valid dotted identifiers; arbitrary keys are an eval-injection surface (localhost-only today, but the WS port has zero auth — anything on the machine can drive the browser).
- Server _cps only tracks /strudel/cps — if a track's code embeds .cps() via /strudel/send, server state (and any future beat-phase bridge) desyncs; make /strudel/cps the single tempo authority in the overhaul.
- The video player target has no REST route and no _execute_step support — usable only via raw WS 'execute' relay until routes are added; video steps therefore can't be recorded/replayed in shows today.
